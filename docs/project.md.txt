# SecureMesh AI — Complete Project Build Specification

## 1. Project Overview

**SecureMesh AI** is an edge-AI-based cybersecurity system for an **ESP32 IoT mesh network**.

The system creates a multi-node wireless mesh where ESP32 devices communicate with one another. The network continuously collects communication telemetry such as packet rate, packet loss, latency, RSSI, retransmissions and sequence behaviour.

An edge computer/gateway analyzes this data using an **AI-based Intrusion Detection System (IDS)**.

When abnormal behaviour is detected, the system:

1. Identifies the suspicious node.
2. Classifies the possible attack.
3. Generates an alert.
4. Isolates the suspicious node.
5. Finds an alternative route.
6. Restores communication through the healthy part of the mesh.
7. Records the complete event.
8. Displays everything through a web dashboard.

The EDI specification describes this overall flow as:

**Initialize → Discover → Establish Mesh → Communicate → Collect Statistics → Extract Features → AI Detection → Identify Attack → Identify Node → Alert → Isolate → Find Alternate Route → Resume Communication → Log → Continue Monitoring.**

# 3. Hardware Layer

## ESP32 Nodes

Use approximately **4–5 ESP32 boards** for the prototype.

Each node should contain:

```text
ESP32
│
├── Wireless communication
├── Node identity
├── Sensor interface
├── Packet handling
├── Mesh participation
├── Telemetry collection
└── Control-command handling
```

Optional sensors:

* DHT11/DHT22 — temperature/humidity
* LDR — light
* MQ-series sensor — gas/air-quality experimentation

The sensors are primarily used to make the network a realistic IoT environment; the cybersecurity component is focused on the network behaviour.

# 4. Mesh Network

The prototype must have **redundant paths**.

For example:

```text
              NODE 2
             /      \
            /        \
        NODE 1 ───── NODE 3
            \        /
             \      /
              NODE 4
```

Possible routes:

```text
NODE 1 → NODE 2 → NODE 3
```

and:

```text
NODE 1 → NODE 4 → NODE 3
```

If NODE 2 becomes unavailable:

```text
NODE 1 → NODE 4 → NODE 3
```

continues to operate.

The project document explicitly requires at least two possible routes between selected nodes so route recovery can be demonstrated.

# 5. Communication Technology

The exact ESP32 networking implementation should be selected during development.

Candidate approaches include:

* ESP-NOW
* ESP-Wi-Fi networking
* ESP-MESH
* Another suitable ESP32-supported mechanism

The project specification intentionally leaves this as an implementation decision. 

Therefore, the software architecture should abstract the networking layer:

```text
MeshNetwork
│
├── initialize()
├── discoverNodes()
├── connect()
├── sendPacket()
├── receivePacket()
├── getNeighbours()
├── getRoutes()
├── removeNode()
└── restoreNode()
```

This prevents the rest of the application from depending directly on one networking implementation.

# 12. Attack Simulation

The project should support controlled testing of four attack categories.

## DoS / Flooding

Abnormally high packet generation.

Possible observable changes:

```text
↑ packet rate
↑ congestion
↑ latency
↑ packet loss
↑ retransmissions
```

The source specifically identifies these as useful behavioural indicators. 

---

## Replay Attack

Previously valid packets are transmitted again.

Potential indicators:

```text
duplicate sequence numbers
unexpected sequence order
repeated timestamps
abnormal packet frequency
```

---

## Spoofing

A device attempts to appear as another node.

Relevant information includes:

```text
Node identity
MAC address
communication pattern
sequence behaviour
```

---

## Rogue Node

An unauthorized ESP32 attempts to participate in the network.

The system should identify that the node is not an authorized participant.

# 16. Self-Healing

The self-healing mechanism is:

```text
DETECT
  ↓
IDENTIFY
  ↓
ISOLATE
  ↓
REROUTE
  ↓
RECOVER
  ↓
MONITOR
```

Example:

### Before

```text
N1 → N2 → N3
```

### N2 compromised

```text
N1 → N2 ✕ N3
```

### Recovery

```text
N1 → N4 → N3
```

The source specifically describes isolation followed by finding an alternate route and resuming communication.

# 17. Route Management

Represent the mesh as a graph:

```text
Node = ESP32
Edge = available communication link
```

Example:

```text
      N2
     /  \
    N1  N3
     \  /
      N4
```

When N2 is blocked:

```text
Remove N2
      ↓
Recalculate graph
      ↓
Find path N1 → N4 → N3
      ↓
Update route
```

A pathfinding algorithm can be used for this layer.

The exact routing mechanism must remain compatible with the selected ESP32 mesh implementation.

# 18. Node Isolation

The edge system sends a command:

```json
{
  "command": "ISOLATE",
  "node": "NODE_02"
}
```

The network then prevents the node from participating in normal forwarding/communication according to the chosen mesh implementation.

This is an important implementation point:

> **Detection happens centrally; enforcement happens in the network.**

## 27. One architectural principle to keep throughout development

Keep these **four layers independent**:

```text
┌────────────────────────────┐
│       PRESENTATION         │
│       Dashboard            │
├────────────────────────────┤
│       INTELLIGENCE         │
│       AI + Decision        │
├────────────────────────────┤
│       NETWORK CONTROL      │
│       Gateway + Recovery   │
├────────────────────────────┤
│       IoT / HARDWARE       │
│       ESP32 Mesh            │
└────────────────────────────┘
```

That way, if you later replace:

* ESP-NOW → another mesh protocol,
* Random Forest → another ML model,
* SQLite → PostgreSQL,
* React → another frontend,

the rest of the project doesn't need to be rewritten.

This is the **general project-building version** I'd use as the master specification for Antigravity. The only things it should determine experimentally rather than assume are the exact ESP32 mesh protocol, physical topology limits, telemetry transport, and ML model performance; those are explicitly left open in the EDI material.
