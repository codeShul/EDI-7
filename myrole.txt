# SecureMesh AI — End-to-End Implementation Specification

## 1. Project identity

**Project name:**

> **SecureMesh AI: An Edge AI-Based Intrusion Detection and Self-Healing Framework for ESP32 IoT Mesh Networks**

The system is a **hardware cybersecurity prototype** consisting of several ESP32 IoT nodes forming a wireless mesh. The nodes exchange data and generate network telemetry. An IDS analyzes this telemetry using ML, detects suspicious behaviour, identifies the affected node, and triggers isolation/recovery so communication can continue through an alternative path. 

The intended environment is a **localized IoT/industrial environment** such as:

* Smart campus
* Industrial IoT
* Warehouse
* Laboratory
* Localized smart-city IoT cluster

It should **not** claim city-wide ESP32 wireless coverage.

# 5. Mesh topology

You need **redundancy**.

Don't build:

```text
N1 → N2 → N3 → N4
```

because if N2 dies, everything after it becomes unreachable.

Instead:

```text
              N2
             /  \
            /    \
          N1 ──── N3
            \    /
             \  /
              N4
```

Now there are multiple possible paths.

For example:

```text
N1 → N2 → N3
```

and:

```text
N1 → N4 → N3
```

If N2 becomes compromised:

```text
N1    X    N2
 \          \
  \          X
   N4 ───── N3
```

Traffic can use:

```text
N1 → N4 → N3
```

The project specification explicitly requires at least two possible routes between selected nodes for recovery testing.

# 12. Attack simulation

Member 2 generates controlled attacks **inside the laboratory network**.

The four required attack categories are:

### DoS / flooding

Attacker generates unusually high traffic.

Expected effects can include:

```text
↑ packet rate
↑ latency
↑ packet loss
↑ retransmissions
↓ delivery
```



### Replay

Previously captured valid messages are retransmitted.

Useful indicator:

```text
duplicate sequence numbers
unexpected sequence ordering
```

The specification specifically identifies sequence-number behaviour as useful for replay detection. 

### Spoofing

A device attempts to appear as another node.

Node identity information becomes relevant.

The specification notes that MAC addresses can be used as an identity-related feature but should **not** be treated as a complete security mechanism. 

### Rogue node

An unauthorized device attempts to participate in the network.

# 16. Self-healing mechanism

This is the project's second major contribution after IDS.

Suppose:

```text
N1 → N2 → N3
```

is currently being used.

Then N2 is identified as compromised.

The system does:

```text
1. Detect abnormal behaviour
2. Identify N2
3. Generate alert
4. Mark N2 compromised
5. Isolate N2
6. Calculate/select alternative path
7. Route traffic around N2
8. Continue communication
9. Record incident
```

This sequence is explicitly defined in the source.

# 17. Route recovery

Your network needs a route-management component.

Conceptually:

```python
find_alternative_route(
    source,
    destination,
    blocked_nodes
)
```

Example:

```text
Before:

N1 → N2 → N3

After N2 isolation:

N1 → N4 → N3
```

The algorithm could use a graph representation:

```text
Nodes = ESP32 devices
Edges = available communication links
```

Then calculate a valid path excluding compromised nodes.

The exact routing implementation depends on the chosen ESP32 networking protocol and therefore should not be falsely hard-coded as an existing feature.

# 28. One important correction before you give this to Antigravity

There are **two different architectural visions** in your existing project material:

The formal EDI specification describes **edge/local-computer AI**: ESP32 nodes remain lightweight and an edge gateway/PC performs heavier inference. 

The separate pitch document describes a more ambitious architecture in which **every node runs a lightweight AI model locally**, with decentralized detection and no cloud round trip. 

**Do not make Antigravity implement both simultaneously.**

For the actual EDI prototype, I would treat the **EDI.txt architecture as the authoritative implementation specification**: lightweight ESP32 nodes + gateway/edge AI. The per-node AI approach can remain a **future/advanced extension** unless your team experimentally demonstrates that it is feasible on your chosen ESP32 setup.
